# Runbook: деплой EMS edge на Siemens IOT2050

Едж-контролер `cmd/edge` (shadow-режим: читає SmartLogger, рахує
віртуальний диспатч, **нічого не пише** в регістри). Артефакти
деплою — у `deploy/edge/`, збірка — через `Makefile`.

Політика оновлень: версії pinned, rollout **ручний** (без watchtower і
авто-оновлень). Одна версія = один тег git → один tarball.

## 1. Артефакти

| Файл на пристрої | Звідки | Призначення |
| --- | --- | --- |
| `/opt/ems-edge/ems-edge` | `dist/ems-edge-linux-arm64` | статичний бінарник (CGO вимкнено) |
| `/etc/systemd/system/ems-edge.service` | `deploy/edge/ems-edge.service` | systemd-юніт, `Restart=always` |
| `/etc/ems-edge/config.yaml` | на базі `config.edge.example.yaml` | конфіг сайту (без секретів) |
| `/etc/ems-edge/edge.env` | на базі `deploy/edge/edge.env.example` | хости SL, URL хмари, Bearer-токен; `chmod 600` |
| `/etc/ems-edge/huawei_smartlogger.yaml` | `registers/huawei_smartlogger.yaml` | каталог регістрів |
| `/var/lib/ems-edge/` | створює systemd (`StateDirectory`) | blackbox SQLite + кеш manifest |

У `/etc/ems-edge/config.yaml` відносно прикладу міняються шляхи:

```yaml
register_catalog: /etc/ems-edge/huawei_smartlogger.yaml
blackbox:
  db_path: /var/lib/ems-edge/blackbox.db
manifest:
  cache_path: /var/lib/ems-edge/active_manifest.json
```

## 2. Передумови

1. **Хмара.** На ВМ в оточенні API задано токен сайту:
   `EDGE_SITE_TOKENS="ab=<token>"` (кілька сайтів — через кому). Після
   рестарту API в логах має бути `api_edge_ingest_enabled`.
2. **Мережа з пристрою.** IOT2050 бачить SmartLogger по `502/tcp` і
   хмару по HTTPS. Перевірка з пристрою:

```bash
nc -vz "$EDGE_SL_HOST" 502
curl -sS -o /dev/null -w '%{http_code}\n' "$EDGE_CLOUD_URL/healthz"
```

3. **Час.** `timedatectl` → NTP synchronized: yes (тики й звірка з
   PCAP залежать від коректного часу).
4. **Journald на диск** (щоб логи переживали ребут):

```bash
sudo mkdir -p /var/log/journal && sudo systemctl restart systemd-journald
```

## 3. Збірка й пакування (на робочій машині)

```bash
make edge-package
# → dist/ems-edge_<git-describe>_linux_arm64.tar.gz
```

Tarball містить бінарник, юніт, приклади env/config і каталог
регістрів. Версію бінарника перевіряють `ems-edge -version`.

## 4. Перший деплой

```bash
# 1. Скопіювати пакет на пристрій
scp dist/ems-edge_*_linux_arm64.tar.gz iot2050:/tmp/

# 2. На пристрої: розпакувати й розкласти
ssh iot2050
sudo useradd --system --home /var/lib/ems-edge --shell /usr/sbin/nologin ems-edge 2>/dev/null || true
mkdir -p /tmp/edge-pkg && tar -C /tmp/edge-pkg -xzf /tmp/ems-edge_*_linux_arm64.tar.gz

sudo install -d /opt/ems-edge /etc/ems-edge
sudo install -m 755 /tmp/edge-pkg/ems-edge /opt/ems-edge/ems-edge
sudo install -m 644 /tmp/edge-pkg/huawei_smartlogger.yaml /etc/ems-edge/
sudo install -m 644 /tmp/edge-pkg/config.edge.example.yaml /etc/ems-edge/config.yaml
sudo install -m 600 /tmp/edge-pkg/edge.env.example /etc/ems-edge/edge.env
sudo install -m 644 /tmp/edge-pkg/ems-edge.service /etc/systemd/system/

# 3. Відредагувати конфіг і env під сайт
sudoedit /etc/ems-edge/config.yaml   # site_id, топологія, шляхи з §1
sudoedit /etc/ems-edge/edge.env      # хости SL, EDGE_CLOUD_URL, токен

# 4. Запуск
sudo systemctl daemon-reload
sudo systemctl enable --now ems-edge
```

## 5. Перевірка після деплою

```bash
systemctl status ems-edge                      # active (running)
journalctl -u ems-edge -f                      # JSON-логи: edge_start, poll ok
sudo sqlite3 /var/lib/ems-edge/blackbox.db \
  "SELECT COUNT(*) FROM telemetry_raw; SELECT COUNT(*) FROM control_decisions;"
```

Локальна веб-консоль (стан, діагностика, manifest, emergency override):
`http://<ip-пристрою>:8081` — доступна тільки з LAN обʼєкта; порт і
вимкнення — секція `local_ui` конфіга.

Консоль відкривається лише з логіном і паролем (HTTP Basic, браузер
питає їх сам). Пароль задається на самому пристрої, з root:

```bash
ssh -t root@<ip-пристрою> /opt/ems-edge/ems-edge -config /etc/ems-edge/config.yaml -set-console-password
```

- Логін за замовчуванням `operator`, пароль вводиться двічі без
  відображення, щонайменше 10 символів. Діє одразу, без перезапуску;
  тією самою командою пароль змінюють.
- Зберігається лише солений хеш: `/var/lib/ems-edge/console_password.json`
  (поруч із `write_pin.json`, шлях — `local_ui.password_path`), права `0600`.
- Поки пароль не задано, консоль на кожен запит відповідає `503`.
  **Задайте пароль перед оновленням пристрою на збірку з цим входом.**
- Після 5 різних невірних паролів з однієї адреси вона блокується на
  15 хвилин (`429`, подія `CONSOLE_LOGIN_LOCKED`); інші адреси працюють
  далі. Той самий невірний пароль, який браузер повторює з кожним
  опитуванням консолі, рахується як одна спроба.
- Дії (override, запис, команди) приймаються лише із заголовком
  `X-Requested-With` — консоль надсилає його сама, це захист від CSRF.
- Консоль працює по HTTP: пароль іде мережею обʼєкта у base64, без
  шифрування.

На хмарі:

- `edge_heartbeats` має свіжий рядок сайту (heartbeat кожні 30 с);
- телеметрія приходить під org `<site>-edge` (суфікс шатл-фази,
  `EDGE_ORG_SUFFIX`);
- `control_decisions` наповнюється, `would_write_*` присутні,
  реальних записів у SmartLogger немає (mode=shadow це гарантує збіркою).

## 6. Логи й діагностика

```bash
journalctl -u ems-edge -f                        # хвіст
journalctl -u ems-edge --since -1h -o cat | jq . # JSON красиво
journalctl -u ems-edge | grep -E 'SL_POLL_FAIL|DISPATCH_DEGRADED|SHADOW_ANOMALY'
```

Черга на відвантаження (росте тільки в офлайні):

```bash
sudo sqlite3 /var/lib/ems-edge/blackbox.db \
  "SELECT 'telemetry', COUNT(*) FROM telemetry_raw WHERE uploaded=0
   UNION ALL SELECT 'decisions', COUNT(*) FROM control_decisions WHERE uploaded=0
   UNION ALL SELECT 'events', COUNT(*) FROM events WHERE uploaded=0;"
```

Актуальний manifest: `cat /var/lib/ems-edge/active_manifest.json | jq
'{manifest_id, mode, preset, valid_until}'`. Прострочений manifest —
очікуваний стан деградації: engine переходить на
`self_consumption_safe` і пише подію `DISPATCH_DEGRADED`.

## 7. Оновлення версії

```bash
make edge-package
scp dist/ems-edge_*_linux_arm64.tar.gz iot2050:/tmp/
ssh iot2050
tar -C /tmp -xzf /tmp/ems-edge_*_linux_arm64.tar.gz ./ems-edge ./huawei_smartlogger.yaml
sudo cp /opt/ems-edge/ems-edge /opt/ems-edge/ems-edge.prev   # для відкату
sudo install -m 755 /tmp/ems-edge /opt/ems-edge/ems-edge
# Catalog grows with the binary (new FC3 keys). Copy it when the
# release adds registers; leftover YAML is safe only if the new keys
# are unused.
sudo install -m 644 /tmp/huawei_smartlogger.yaml /etc/ems-edge/huawei_smartlogger.yaml
sudo systemctl restart ems-edge
/opt/ems-edge/ems-edge -version && journalctl -u ems-edge -n 20
```

Blackbox і кеш manifest живуть у `/var/lib/ems-edge` і оновлення
переживають; черга `uploaded=0` після рестарту довантажується сама.

Після оновлення приберіть пакет і розпаковані файли з `/tmp`: на
IOT2050 це `tmpfs`, тобто оперативна пам'ять.

**Доставка команд із пульта.** Manifest опитується раз на 5 с:
незмінний повертається як 304. Щойно застосовано нову версію, edge
одразу вивантажує журнал, і хмара бачить «застосовано» за кілька
секунд. Поки версія в дорозі, пульт оновлює стан кожні 3 с і пише
«в дорозі до контролера». Якщо в конфігу пристрою явно стоїть
`manifest.poll_interval: 60s`, замініть на `5s` під час деплою, з
дозволу власника (конфіг під контрольною сумою).

## 8. Відкат

```bash
sudo cp /opt/ems-edge/ems-edge.prev /opt/ems-edge/ems-edge
sudo systemctl restart ems-edge
```

Схема blackbox створюється ідемпотентно (`CREATE TABLE IF NOT
EXISTS`), тому відкат на попередню версію безпечний для даних.

## 9. Recovery

- **Сервіс у рестарт-циклі.** `journalctl -u ems-edge -n 50`: майже
  завжди це конфіг (`edge_config`) або відсутній env. Юніт з
  `StartLimitIntervalSec=0` ретраїть вічно — після виправлення нічого
  скидати не треба.
- **Пошкоджений blackbox** (`database disk image is malformed`):

```bash
sudo systemctl stop ems-edge
sudo mv /var/lib/ems-edge/blackbox.db /var/lib/ems-edge/blackbox.db.corrupt.$(date +%s)
sudo systemctl start ems-edge     # схема створиться заново
```

  Невивантажений залишок можна пізніше дістати з `.corrupt.*` через
  `sqlite3 .recover`.
- **Повний диск.** Ретеншн сам чистить (30 днів; при ≥95 % диска —
  видалення uploaded oldest-first). Якщо диск забив хтось інший —
  звільнити місце і перезапустити сервіс.
- **Довгий офлайн хмари.** Нічого не робити: uplink ретраїть з
  backoff, blackbox накопичує. Ємності 30 днів вистачає з запасом.

## 9а. Пілот ze — фактичні параметри (2026-08-25)

Перевірені на живому розгортанні значення, які відрізняються від
прикладів вище:

- **unit_id: 99** для обох SmartLogger-ів (вендорська документація

- **`ess_discharge_sign` для ze не задавати** (за замовчуванням `1`: сирий

  лічильник розряду +317.9 кВт·год, заряду +0, SOC 70.4 → 50.8 %;

- **`limits.bess` — паспорт ze: `rated_power_kw: 864`,
  `rated_capacity_kwh: 1720`** (не значення з прикладу 324/645!).
  Від rated рахується поріг `SHADOW_ANOMALY` (1.5×rated) і fallback
  клампів, коли SL не віддає 40490/40492 — живий інцидент 2026-09-04:
  експортні розряди плану 733–791 кВт сипали аномаліями, поки в
  конфізі стояло 324;
- **PV-логер (10.28.40.101) має Modbus TCP-обмеження клієнтів**:
  нову IP контролера треба додати у веб-інтерфейсі SmartLogger
  (Налаштування → Комунікації → Modbus TCP), інакше «connection reset
  by peer» одразу після запиту. ESS-логер (.102) пускав без змін;
- **мережа майданчик→сервер закрита** (ініціація лише ВМ→майданчик).
  Тимчасове рішення — реверс-SSH-тунель з ВМ, юніт
  `/etc/systemd/system/edge-tunnel-ze.service` (ssh -R
  18080:localhost:8080 root@10.28.40.88), а на пристрої
  `EDGE_CLOUD_URL=http://127.0.0.1:18080`. Постійне — заявка мережевику
  на TCP 8080 з підмережі майданчика до ВМ, після чого тунель
  прибирається;
- телеметрія shadow-фази в хмарі лежить під org **`ze-edge`**
  (EDGE_ORG_SUFFIX), рішення — у `control_decisions`.

## 9б. Режим «Керування» у веб-додатку

Хмарна консоль керування — не окремий застосунок, а другий режим
основного дашборда. Перемикач «Аналітика та моніторинг | Керування»
у верхній панелі (поряд із пікером об'єкта); режим «Керування» =
`?view=control`, старі посилання `?view=planner` редіректяться у
вкладку «План УЗЕ».

Вкладки:

- **Стан** — live-потоки як на дашборді + «Команда УЗЕ (shadow)»
  (останній запис `control_decisions`), «Стан керування» (SOC-резерв,
  ліміт імпорту, heartbeat, черга на пристрої) і Energy Trend
  «план і факт»: інтервали чинного manifest накладаються на фактичні
  серії, вертикальний маркер — момент MANIFEST_APPLIED;
- **План УЗЕ** — пульт ручного керування (ems-spec
  `docs/specs/ems_manual_control_mvp.md`): споживання, команди й
  обмеження на 24 год → `POST /api/v1/dispatch/confirm` зберігає версію
  (`dispatch_versions`) і одразу публікує manifest. Кожні 15 хв
  `RunEdgePlannerLoop` перераховує LP застосованої версії від
  поточного SOC; інтервали — лише на години з введеним споживанням і
  ціною РДН, без них план порожній і edge працює на самоспоживання;
- **Режими** — опис пресетів edge (`economic_arbitrage` /
  `self_consumption` / `self_consumption_safe`) і який із них чинний;
  ручного погодинного плану й `publish-manual` більше немає;
- **Обмеження** — `GET/PUT /api/v1/edge/settings` (SOC target/reserve,
  ліміти заряду/розряду, ліміт і ціль імпорту, номінал СЕС, режим
  відпуску й технічний ліміт експорту PCC). Значення перекривають
  паспортні й потрапляють у `limits`/`soc_policy` кожного наступного
  manifest; «Опублікувати» = `POST /api/v1/edge/manifest/publish`;
- **Журнал** — версії manifest зі статусом доставки + стрічка
  `edge_events`.

Статусні чипи верхньої панелі живляться з
`GET /api/v1/edge/status?site_id=` (poll 15 с у консолі) та
`GET /api/v1/edge/fleet` (дашборд, 60 с): «IOT2050 online» = heartbeat
молодший за 180 с; стан manifest = applied/pending/expired за подією
MANIFEST_APPLIED і `valid_until`.

Нові таблиці (`edge_site_settings`) API створює сам при старті
(`InitEdgeSchema`), окремих кроків міграції на ВМ не потрібно;
дзеркальні SQL-файли — `migrations/014_edge_site_settings.sql`.

## 9в. Запис у SmartLogger (тест на ЖЕ, ems-spec `ems_sl_write_cutover.md`)

Збірка вміє писати в логери, але лише поки ввімкнений **прапорець запису на самому IOT2050**. За замовчуванням він вимкнений, і після будь-якого перезапуску сервісу теж вимкнений (подія `WRITE_OFF_AFTER_RESTART`). З хмари його ввімкнути не можна: manifest із `write_enabled: true` edge відхиляє. Вмикає його людина на локальній консолі, з кодом об'єкта і PIN.

**PIN.** Задається лише на самому пристрої, з root. Поки PIN не задано, увімкнення неможливе:

```bash
ssh -t root@10.28.40.88 /opt/ems-edge/ems-edge -config /etc/ems-edge/config.yaml -set-write-pin
```

- PIN вводиться двічі без відображення, щонайменше 6 символів, і діє одразу, без перезапуску. Тією самою командою PIN змінюють.
- Зберігається лише солений хеш: `/var/lib/ems-edge/write_pin.json`, права `0600`.
- Після 5 невірних PIN введення блокується на 15 хвилин (подія `WRITE_ENABLE_DENIED`).
- Стоп і вимкнення працюють без PIN, але, як і вся консоль, лише після входу з паролем консолі (розділ 5, `-set-console-password`).

Порядок нижче — за погодженою редакцією cutover від 04.11.2026.

**Що пише.**
- **Циклічно.** На логер СЕС кожні ~2 с — `40378` (стеля СЕС) і `40384` = 0. На логер УЗЕ кожні ~3 с — `40381` (+ розряд / − заряд) і `40386` = 0. Після кожного запису той самий регістр читається назад.
- **Разово, лише кнопкою.** FC06 зі значенням 0, без readback:
  - СЕС: `40197` пуск, `40196` зупинка;
  - УЗЕ: `40199` пуск, `40198` зупинка;
  - масив: `40200` пуск, `40201` зупинка, окремо для логера СЕС і логера УЗЕ.

  `40202`/`40203` та інших адрес збірка не пише ніколи. Автопуску немає.

**У хмарі перед тестом — стеля відпуску.** «Керування → Налаштування» → «Режим відпуску»: для ЖЕ «Самовиробництво — 50 % договірної потужності», це 850 кВт при 1 700. «Технічний ліміт експорту PCC» і нижчий ліміт у пульті її знижують. IOT2050 отримує стелю в manifest протягом 15 хв після збереження. `limits.grid.export_cap_kw` у конфігу пристрою діє лише, поки чинного manifest немає. Без стелі запис не вмикається.

**Конфіг пристрою перед тестом:**
- знаки PCC — `meter_import_sign: 1`. 16.11 о 19:32 на ЖЕ, коли було темно і батарея заряджалася (тобто йшов імпорт), `40505` = +1275 кВт, `32278` = +1278 кВт. `40505` уже «+ імпорт», тому `grid_import_sign` не змінюємо. Лічильник на ЖЕ, всупереч карті Huawei, теж показує імпорт із «+». Без цього рядка передумова «знак PCC» не пустить увімкнення;
- кількість слів аварій за прошивкою логерів: `smartlogger.alarm_words: 6` для старшої карти (`50000…50005`). За замовчуванням 8 (карта Issue 52), з переходом на шість, якщо логер відмовить на `50006`/`50007`;
- решта — секція `control.write` (утримання 15 хв, перша команда ≤ 100 кВт, SOC 20–90 %).

Консоль: `http://10.28.40.88:8081` (з ВМ напряму або через `ssh -L`), вкладка «Стан», картка «Запис у SmartLogger».

**Кроки 2–3: стик.**
1. Інсталятори віддалено зупиняють УЗЕ, графік Encombi не редагують. Записати, чи сонце ще виробляє.
2. Розгорнути «Передумови увімкнення»: усі мають бути ✅. Серед них:
   - PIN задано;
   - **УЗЕ зупинена (`40540` ≠ 0)**;
   - свіжа телеметрія, обидва логери на зв'язку;
   - слова аварій усі 0, `40737` = 4 на обох логерах;
   - номінал `40396` прочитано, якщо СЕС у роботі;
   - SOC і `40490`/`40492` відомі;
   - стеля відпуску і ліміт імпорту задані, імпорт не біля ліміту;
   - напруги в нормі, знаки `40505` і `32278` узгоджені;
   - чинний manifest пронумерований.

   «Лічильник PCC не відповідає» означає, що логер СЕС не бачить лічильника в точці приєднання: `40505` без даних, фази лічильника 0 В або без даних. На ЖЕ 17.11 так було з 13:48 до 14:25, хоча шина весь час була під напругою 222–226 В. Треба перевірити живлення лічильника (на ЖЕ DTSU666-HW) і його RS-485 до логера СЕС, адреса 11. Без фаз лічильника «мережа є» не проходить: самих лінійних напруг логерів не досить. Поки лічильник не повернеться, запис не вмикається, а увімкнений зупиняється за 10 с.
3. Зняти адресу Encombi з обох логерів.
4. Одразу ввести код об'єкта (`ze`) і PIN, натиснути «Увімкнути запис» і підтвердити.

Після увімкнення в логери йде лише `40381` = 0 і `40378` = номінал. Пуск не надсилається, стан — «УЗЕ не запущена». Те саме скриптом: `POST /api/write {"action":"enable","confirm":"ze","pin":"…"}`; стан і передумови — `GET /api/write`.

**Режим PCS — лише PQ (cutover §12.7).** Одразу після «Увімкнути запис», поки УЗЕ стоїть, edge сам один раз пише `44365` = 0 на логер УЗЕ. Біля «Пуск УЗЕ» видно режим: `44364` = 0 означає PQ, 1 — VSG. «Пуск УЗЕ» і «Пуск масиву» на логері УЗЕ активні лише в PQ. Якщо за 30 с режим не став PQ, пуск не надсилається. Тоді треба перевірити на місці перемикач PQ/VSG, вимкнути запис і ввімкнути його знову. Якщо після пуску `44364` ≠ 0 довше 10 с, edge зупиняє запис. Перше таке увімкнення робимо при інсталяторах.

**Крок 4: перевірка масивів і пуск.** Кнопки в таблиці «Пуск і зупинка» працюють лише з увімкненим записом.
1. Перевірку масивів роблять, лише якщо сонце працює, а імпорт разом із сонцем не біля 1 700 кВт:
   1. «Зупинка» в рядку «Масив логера УЗЕ». Через 30 с консоль записує, чи сонце лишилось (`ESS_ARRAY_STOP_PV_CHECK`).
   2. «Зупинка» в рядку «Масив логера СЕС»: сонце має зійти на 0.
   3. «Пуск» обох масивів. Якщо пуск назад не підтверджено, добу не починають.
2. «Пуск» УЗЕ, якщо пуск масиву УЗЕ її ще не підтвердив. «Пуск» СЕС, якщо сонце не виробляє. Під час розгону СЕС `40396` росте з кожним інвертором, і `40378` іде за ним. Readback нижчий за записане означає, що логер обрізав стелю до доступної потужності. Це не відмова, у консолі біля `40378` так і написано.
3. Поки пуск УЗЕ не підтверджено, `40381` = 0, а ручні команди й автомат у логер не йдуть.
4. 15 хвилин утримання на 0 кВт рахуються від підтвердженого пуску УЗЕ. Далі команди за пріоритетом: ручний блок із пульта, план, самоспоживання.

Одразу після утримання, якщо в пульті немає ручного блока на цю годину і плану немає, автомат самоспоживання сам почне розряд на покриття імпорту (перша команда до 100 кВт, далі до дефіциту). Щоб батарея стояла на 0 до першої ручної команди, заздалегідь поставте в пульті блок «Пауза» на ці години.

**Зворотний зв'язок біля кожної кнопки.**
1. Відповідь логера: «прийняв», «відмова» з кодом exception або «немає відповіді» (через 15 с).
2. Підтвердження за станом протягом 3 хвилин, з відліком часу і живими значеннями:
   - пуск УЗЕ — `40540` = 0 і `40539` > 0;
   - зупинка УЗЕ — `40540` ≠ 0;
   - пуск СЕС — `40388` > 2 кВт;
   - зупинка СЕС — `40388` = 0 і жодного інвертора в мережі.

Поки команда чекає, обидві кнопки її рядка неактивні. Повтор сам не надсилається.

**Кожна команда обрізається:**
- SOC 20–90 % і межі `40490`/`40492`;
- перша ненульова — до 100 кВт, поки батарея її не виконала;
- відпуск у точці приєднання не вище стелі: спершу зменшується розряд, потім `40378`;
- стеля СЕС нижча на частку інверторів у несправності.

**Зупинки.** Зупинка тримається до вимкнення запису: УЗЕ 0 кВт, СЕС на номіналі, запис триває, щоб логер не пішов у таймаут. Причини:
- будь-яке слово аварії з набору ≠ 0;
- УЗЕ знову зупинилась **після підтвердженого пуску** (`40540` ≠ 0; до пуску це очікуваний стан);
- `40737` ≠ 4;
- телеметрія несвіжа довше 10 с;
- фазна напруга < 200 В або лінійна < 350 В довше 10 с;
- імпорт ≥ 95 % ліміту довше 5 с;
- відпуск понад стелю довше хвилини;
- батарея не виконує команду довше 30 с.

Автоматична зупинка ще й сама надсилає «Зупинку УЗЕ», якщо тест її запускав, і «Зупинку СЕС», якщо тест запускав сонце. «Тест запускав» означає, що логер прийняв команду пуску, навіть якщо пуск ще не підтверджено: тоді зупинка йде поверх пуску, що чекає. Зупинка УЗЕ надсилається і тоді, коли PCS уже сам вимкнувся. Повторний пуск після зупинки не надсилається. «УЗЕ 0 кВт (стоп)» ставить лише уставку 0, батарею не зупиняє. Далі — «Вимкнути запис» і повернення Encombi.

**Логер СЕС.** Exception 4 на `40378`/`40384`, поки сонце не в роботі (зупинене або вночі), — очікувана відповідь: запис триває, УЗЕ не зупиняється (події `PV_WRITE_REFUSED` / `PV_WRITE_ACCEPTED`). Так само не є відмовою readback, що не збігся, поки сонце не в роботі. Під час зупинки чи пуску логер починає відмовляти раніше, ніж оновиться `40388`, тому exception 4 при сонці «в роботі» терпиться 30 с і лише потім стає `WRITE_FAULT`. О 10:00, якщо сонце не в роботі, подія `PV_NOT_RUNNING`: тоді «Пуск СЕС».

**Логер УЗЕ.** Будь-яка його відмова — `WRITE_FAULT`, так вимагає бриф. Якщо на стику виявиться, що логер УЗЕ не приймає `40381` при зупиненій УЗЕ (exception 4 одразу після увімкнення запису), є перемикач у конфігу пристрою: `control.write.tolerate_stopped_ess_refusal: true`. З ним логер УЗЕ трактується як логер СЕС: відмова очікувана, поки УЗЕ зупинена (події `ESS_WRITE_REFUSED` / `ESS_WRITE_ACCEPTED`). За замовчуванням вимкнено; вмикати лише за рішенням власника, бо це відступ від брифу.

На ЖЕ напруга під час вечірнього заряду великою потужністю часто нижча за ці пороги (16.11 18:00–20:00 фаза нижче 200 В у 59 % вибірок). Тест краще вести вдень; деталі — `docs/spec-remarks/sl_write_cutover.md`.

**Відмова запису.** Помилка запису, readback, що не збігся, або записувач 10 с не може з'єднатися з логером: УЗЕ 0 кВт, зупинка УЗЕ (якщо тест її запускав) і зупинка СЕС (якщо тест її запускав), потім прапорець знімається сам (`WRITE_FAULT`).

**Вимкнення (крок 5).** «Вимкнути запис»:
1. IOT2050 пише УЗЕ 0 і СЕС на номіналі, чекає readback.
2. Надсилає «Зупинку УЗЕ» (наприкінці завжди) і чекає `40540` ≠ 0.
3. Якщо тест запускав сонце — «Зупинку СЕС».
4. Лише тоді знімає прапорець.

Якщо крок не підтвердився, це записується в причину вимкнення, і прапорець однаково знімається. Потім повернути адресу Encombi. Сонце, яке працювало весь час без нашого пуску, не гаситься.

**Журнал.**
- Події запису: `WRITE_ENABLED`, `WRITE_STOP`, `WRITE_FAULT`, `WRITE_DISABLED`, `MANUAL_COMMAND_CLAMPED`.
- Події кнопок: `SL_COMMAND_SENT` (хто, регістр, логер), `SL_COMMAND_REFUSED`, `SL_COMMAND_NO_RESPONSE`, `SL_COMMAND_CONFIRMED`, `SL_COMMAND_NOT_CONFIRMED`, `ESS_ARRAY_STOP_PV_CHECK`.
- Окремі поля в `control_decisions`: `write_state` (зокрема `await_start`), `command_40381`/`command_40378`, `written_*`, `readback_*`, `write_clamps`, `manual_command_id`.
- У хмарі на вкладці «Стан» — картка «Запис у SmartLogger»: хто пише, стан УЗЕ і СЕС, остання кнопка з відповіддю і підтвердженням, команда, readback, аварії. Кнопок у хмарі немає.

## 9г. Робота без мережі на ЖЕ (ems-spec `ems_offgrid_island_generator.md`)

Усе, що нижче, вимкнене в конфігу за замовчуванням. Поки вимкнене, edge поводиться як раніше. Вмикати на ЖЕ лише з вимкненим записом і з дозволу власника, по одному кроку.

**Читання Encombi (§4.1).** Секція `encombi` конфігу: `enabled: true`, `host: 10.28.40.103` (FC04, unit 1, лише читання). Раз на секунду IOT2050 читає входи `20500`, лічильник генератора (потужність `0`, напруга шини `38`/`40`/`42`) і ознаку зв'язку лічильника `199`. Нічого не пише.

Що з'являється:
- рядок стану вгорі вкладки «Стан» і `health.supply` у heartbeat: живлення, перемикач на шафі, режим УЗЕ, хто керує, обмеження; у режимах «Генератор» і «Острів» — навантаження генератора, заряд і час до 20 %;
- події `SUPPLY_MODE_CHANGED` і `CABINET_SWITCH_CHANGED`;
- у такті ключі `encombi_di_bits`, `gen_meter_power_kw`, `gen_bus_voltage_*_v`, `gen_meter_alive`; у blackbox — `di_state_json`.

Режим живлення (§4.2): «мережа» — реле **і** замкнений ввід того самого вводу; «генератор» — замкнений вимикач генератора і напруга шини від 180 В (`bus_live_min_v`); «острів» — шина під напругою без мережі й генератора; «знеструмлено» — шина без напруги. Дані старші за 5 с або `199` ≠ 1 — «невідомо». Новий режим береться, коли тримається 2 с. На ЖЕ лічильник генератора замовкає через ~30 с знеструмлення (`199` = 0), тож консоль показує «Невідомо», доки острів чи мережа не дадуть напругу.

26.11.2026 разове читання з IOT2050 дало `20500` = `0x01CE` (мережа через Т1, перемикач у PQ), шину 228–231 В при генераторі 0 кВт, відповідь 30–180 мс. З 26.11.2026 21:31 читання на ЖЕ ввімкнене постійно, разом із `manifest.poll_interval: 5s`; хмарний колектор Encombi від цього не постраждав. Острів під Encombi на ЖЕ буває щодня по 12–17 год, тому «Острів» на консолі — звичайний стан. Деталі й відкриті питання — `docs/spec-remarks/offgrid_island_generator.md`.

**Запис і режим живлення (§2, §4.3).** Діє лише з увімкненим читанням Encombi. Сама система нічого не запускає і режимів не перемикає; автоматично вона лише ставить УЗЕ на 0 і зупиняє.
- Увімкнути запис можна лише від мережі з перемикачем у PQ (передумова «живлення»).
- **Мережа зникла:** режим «знеструмлено», «острів» або «генератор» тримається 2 с. Тоді УЗЕ 0 кВт, «Зупинка УЗЕ» і «Зупинка СЕС», якщо тест їх запускав (подія `WRITE_MODE_STOP`, стан `mode_stop`). Прапорець запису лишається. PCS вимикається одразу зі зникненням мережі, тому, поки новий режим не прийнято, перевірки зупинки чекають до 5 с, а УЗЕ стоїть на 0.
- **Острів не від «Пуск острова»:** шину тримає УЗЕ у VSG (`44364` = 1), а підняла острів інша система чи людина на логері. На ЖЕ так робить Encombi за 2–3 хв після зникнення мережі. Уставки УЗЕ (`40381`, `40386`) не пишуться, стеля СЕС за §5.2, стеля експорту не діє (подія `ISLAND_EXTERNAL`). Сама система нічого не зупиняє ні після зникнення мережі, ні при вимкненні запису: зупинка знеструмила б об'єкт. Кнопки зупинок доступні, як завжди.
- **Мережа повернулась:** стан «УЗЕ не запущена», уставка 0. «Пуск УЗЕ» натискає людина, далі утримання й план.
- **Перемикач не в PQ при мережі, перехід або застарілі дані Encombi:** УЗЕ 0 кВт без зупинки; перевірки мережі з cutover діють.
- **Недоступні дії.** Недоступна кнопка сіра, причина поруч і в рядку стану (`health.supply.actions`). Зупинки доступні завжди. Ручна команда з хмари, недоступна в цьому режимі, не виконується: УЗЕ 0 і подія `MANUAL_COMMAND_UNAVAILABLE`.

**З генератором (§6).** Потрібно `offgrid.generator_enabled: true`, за замовчуванням вимкнено. Генератор запускають і зупиняють люди, IOT2050 цього не робить.
- **Кнопка «Пуск УЗЕ з генератором»** — у блоці «Робота без мережі», з PIN. Активна, коли шину живить генератор, перемикач у PQ, УЗЕ зупинена після зникнення мережі. Порядок: `44365` = 0, якщо PCS ще не в PQ, підтвердження, `40199`, підтвердження (стан `gen_run`). Звичайний «Пуск УЗЕ» від генератора закритий.
- **Керування.** Зарядом УЗЕ генератор тримається біля 480 кВт, не нижче 220 кВт. Заряд зростає не більше ніж на 50 кВт за секунду, перша команда до 100 кВт. Розряд лише на те, що понад номінал 734 кВт. При заряді 90 % (або на рівні «заряду до рівня») заряд 0; якщо генератор нижче 220 кВт, знижується стеля СЕС, а без сонця — подія `GEN_BELOW_MIN`.
- **Захисти.**
  - Генератор ≤ 0 кВт довше 2 с: розряд 0, стеля СЕС донизу, `GEN_REVERSE_POWER`.
  - Дані Encombi старші за 5 с: розряд 0, заряд тримається; старші за 30 с — і заряд 0, `GEN_DATA_STALE`. УЗЕ не зупиняється, дані повернулись — керування йде далі.
  - Перевірки мережі (напруга, лічильник PCC, імпорт і відпуск) не діють; решта перевірок cutover діє.
- **Ручні команди з хмари.** Діють лише «пауза» і «заряд до рівня».
- **Зупинка.**
  - Вимикач генератора розімкнувся або шина без напруги: УЗЕ 0 і `40198`, сесія лишається.
  - «Зупинка УЗЕ» оператором теж повертає в очікування: кнопка генератора знову доступна, сонце не гаситься.

**Острів (§5).** Потрібно `offgrid.island_actions_enabled: true`, за замовчуванням вимкнено до відповіді вендора. Але й з увімкненим прапорцем писач відхиляє `44365` = 1, доки не погоджено порядок тесту. Вхід тоді зупиняється на кроці VSG із причиною «заборонений до погодження порядку тесту». Знімає заборону окремий PR (E5).
- **«Пуск острова»** — з PIN. Активна, коли:
  - шина знеструмлена, перемикач у VSG щонайменше 5 с;
  - 1QF, 2QF і вимикач генератора розімкнені, вимикач УЗЕ замкнений;
  - заряд вище 25 %, УЗЕ зупинена, дані Encombi свіжі.
- **Кроки §5.1.** Порядок і паузи — у конфігу (`island_step_pause`, `island_*_timeout`), бо чекають на вендора:
  1. Стеля СЕС 0, пауза.
  2. `40198`, якщо УЗЕ ще працює.
  3. `44365` = 1 і чекати `44364` = 1 до 30 с.
  4. `40199` і чекати до 3 хв на `40540` = 0 і напругу шини від 180 В.
  5. `40197`, якщо сонце не працює.
  
  Невдача: `40198`, якщо треба, і `44365` = 0, причина на консолі (`ISLAND_START_FAILED`). Повтор — новою кнопкою, не раніше `island_retry_after`. Чорного старту немає.
- **Робота §5.2** (стан `island`).
  - `40381` і `40386` не пишуться.
  - Стеля СЕС — номінал до 88 % заряду, вище — не більше за споживання.
  - На 30 % подія `ISLAND_SOC_WARN` «запускайте генератор».
  - Аварія логера, `44364` ≠ 1 або застарілі дані Encombi — лише тривога `ISLAND_ALARM`, без зупинки.
- **Вихід §5.3.** Спрацьовує за будь-якої з умов:
  - «Зупинка острова»;
  - перемикач не у VSG 5 с;
  - замкнувся ввід або вимикач генератора;
  - заряд 20 % (`ISLAND_SOC_LOW`);
  - УЗЕ зупинили.
  
  Порядок: `40198` до `40540` ≠ 0, потім `44365` = 0 до `44364` = 0, далі за режимом живлення. «УЗЕ 0 кВт (стоп)» в острові недоступна. «Вимкнути запис» з острова теж повертає УЗЕ в PQ перед тим, як зняти прапорець.

## 10. Польові тести (spec §13)

### Тест A — паралельний poll ВМ vs IOT2050

RO-паралель двох Modbus-клієнтів підтверджена Photomate, перевіряємо
на ділі:

1. Едж запущений ≥ 1 години поруч зі штатним колектором ВМ.
2. На дашборді ВМ немає розривів/деградації графіків за цю годину
   (перевірити `data_quality` у семплах ВМ).
3. У журналі еджа немає сплеску `SL_POLL_FAIL`.
4. Порівняти криві `active_ess_power_kw` org `<site>` vs `<site>-edge`
   за годину — форма має збігатися (обидва потоки йдуть з кадансом 1 с).

**Критерій:** дашборди ВМ не деградують (sign-off №1).

### Тест B — офлайн 30 хв і догрузка backlog

1. Зафіксувати лічильники `uploaded=0` (SQL з §6).
2. Розірвати WAN (або заблокувати хмару):
   `sudo iptables -A OUTPUT -d <cloud-ip> -j DROP`
3. 30 хв: сервіс живий, `telemetry_raw uploaded=0` росте (~60 рядків/хв
   на метрику), рішення продовжують писатись, у журналі — retry uplink.
4. Відновити мережу: `sudo iptables -D OUTPUT -d <cloud-ip> -j DROP`
5. Черга `uploaded=0` спадає до ~0 (батчі по 600 записів кожні 30 с —
   30-хвилинний backlog догружається за кілька хвилин); на хмарі немає
   дублікатів (ідемпотентність по `batch_id`), у `telemetry_samples`
   немає дірки за вікно офлайну.

**Критерій:** повна догрузка без дублікатів і без дірок.

### Тест C — soak 7 діб

1. Залишити сервіс на ≥ 7 діб.
2. Щодня (або скриптом): heartbeat свіжий; рестартів немає
   (`systemctl show ems-edge -p NRestarts`); диск під контролем
   (`du -h /var/lib/ems-edge`; WAL не росте необмежено).
3. Наприкінці: покриття тиків за кожну добу ≥ 99 %
   (`SELECT date(ts_utc), COUNT(*) FROM telemetry_raw GROUP BY 1` —
   порівняти з теоретичними 86400/добу на метрику з поправкою на
   `poll_interval`), ретеншн відпрацьовує (немає рядків старше 30 діб).

**Критерій:** blackbox ≥ 7 діб безперервного запису (sign-off №2).

### Sign-off (spec §13.3)

1. Дашборди ВМ не деградують при паралельному poll — тест A.
2. Black box ≥ 7 діб безперервного запису — тест C.
3. Shadow decisions генеруються без жодного write у SL — збірка не
   містить коду запису; підтвердити відсутністю FC6/FC16 у трафіку
   еджа (за потреби `tcpdump -i any port 502 -w edge_modbus.pcap`).
4. Reconcile-звіт по `40381` (ze, 3–5 червня) з метриками — команда
   з розділу replay (`tools/shadow_vs_pcap_reconcile.py`).
