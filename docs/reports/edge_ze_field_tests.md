## Тест C — soak 7 діб: покриття 5/7 діб, знайдено й виправлено stall (2026-09-02)

Вікно: 2026-08-26 → 2026-09-02 (7 повних діб). Підсумок за критеріями:

- **Стабільність: ✅.** 0 крешів (`NRestarts=0`, у журналі жодного
  panic/OOM/failed), аптайм пристрою 7 д 23 г без ребутів. Усі 4 старти
  сервісу — планові (25.08 первинний; 01.09 деплой діагностики 13:45 і
  два конфіг-рестарти §10.5).
- **Ретеншн/диск: ✅.** Blackbox 657 тис. тіків / 1.24 ГБ, WAL не росте;
  30-денний зріз ще не настав (пілоту 8 діб).
- **Покриття тиків ≥ 99 %/добу: ❌ 2 доби з 7.** 26.08 100 %, 27.08
  100 %, 28.08 99.99 %, 29.08 99.93 %, 30.08 99.19 %, **31.08 98.53 %**,
  **01.09 97.89 %** (01.09 містить і планові рестарти §10/тест B —
  але й без них доба нижче порога).

Root cause (знахідка soak): щогодинний `Maintain` ретеншну виконував
`DELETE … WHERE ts_utc < cutoff` **без індексу по `ts_utc`** — повний
скан таблиць (уся БД читається з флешу) на єдиному writer-з'єднанні.
Тік-цикл завмирав на час скану: діри рівно щогодини від моменту старту
сервісу (о `:46:16`, після рестарту 15:11Z — о `:11:31`), тривалість
росла з БД: ~25 с (30.08) → ~55–70 с (31.08) → ~75–97 с (01.09). За
місяць добігло б ~5 хв/год (покриття ~91 %).

Фікс (у гілці `edge-shadow-diagnostics`): індекси `idx_*_ts`, DELETE
порціями по 2000 рядків із паузою 50 мс (writer звільняється кожні
кілька мс), той самий бюджет 50к/год для аварійного disk-guard; тести.
Перший старт після оновлення добудовує індекси (~1–2 хв на ГБ) —
одноразова пауза тіків. Re-soak: покриття ≥ 99 %/добу протягом 3 діб після
деплою фіксу.

## Sign-off №3 — shadow без запису: конструктивно

Збірка `121c538` не містить коду запису в SmartLogger (Modbus лише
FC3); рішення зберігаються як `would_write_*`. За потреби
інструментальне підтвердження: `tcpdump -i any port 502` на пристрої —
відсутність FC6/FC16.
