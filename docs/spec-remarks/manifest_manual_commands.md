# Зауваження до специфікацій: ручні команди в manifest

Від команди sestelemetry (хмара + edge) для автора ems-spec. Текст специфікацій ми не змінюємо; тут лише те, чого нам бракує, щоб реалізувати ручні команди пульта і тест першого запису ([ems_sl_write_cutover.md](https://github.com/Agroprosperis/ems-spec/blob/main/docs/specs/ems_sl_write_cutover.md) §4).

Повний чорновий варіант цих пропозицій у вигляді тексту схеми лишився в закритому [ems-spec PR #5](https://github.com/Agroprosperis/ems-spec/pull/5) — можна взяти звідти, якщо підходить.

Поки рішень немає, edge виконує план пульта погодинною потужністю `plan.intervals[].ess_kw` у shadow, без запису в SmartLogger.

---

## 1. У manifest немає місця для ручних команд

**Що зараз.** [ems_manifest_schema.md](https://github.com/Agroprosperis/ems-spec/blob/main/docs/specs/ems_manifest_schema.md) §5: «Ручне» = `operating_mode: manual`, інтервали ігноруються, керує edge UI override. Пульт ([ems_manual_control_mvp.md](https://github.com/Agroprosperis/ems-spec/blob/main/docs/specs/ems_manual_control_mvp.md) §1) і cutover §4 описують інше: оператор задає команду на блок годин у Cloud Console, хмара доставляє її тим самим каналом, що й план, edge перевіряє межі й виконує.

**Чому погодинних кВт не досить.** Хмара рахує кВт із прогнозу споживання. Команда «покривати споживання до 300 кВт» при фактичному споживанні 280 кВт замість прогнозних 200 кВт недовиконується; «ціль SOC 80 %» не досягається, якщо SOC відійшов від прогнозу.

**Пропозиція.** Окремий масив блоків команд у manifest: `command_id`, `from`, `until`, тип, параметр, хто й коли підтвердив. Edge виконує намір щосекунди за поточними вимірами, через той самий ланцюг клампів, що й план. Поки діє блок, економічна уставка не пишеться. «Повернути в AUTO» = хмара прибирає блок.

Набір типів відповідає пульту:

| Пульт | Що робить edge щосекунди |
| --- | --- |
| Пауза | УЗЕ 0 кВт |
| Фіксована потужність (заряд / розряд) | задана потужність |
| Покрити споживання, до N кВт | розряд = min(N, max(0, споживання − СЕС)), без експорту батареєю |
| Заряд від надлишку СЕС, до N кВт | заряд = min(N, max(0, СЕС − споживання)), без мережі |
| Ціль SOC N % до кінця блоку | заряд = енергія, якої бракує ÷ час, що лишився; ціль досягнута → 0 |
| Не перевищити імпорт N кВт | AUTO, але імпорт у точці приєднання ≤ N |
| Експорт через точку приєднання N кВт | обмін PCC = −N |

## 2. Стеля експорту — своя для кожного об'єкта

**Що зараз.** У manifest є лише `export_allowed` (так / ні). Числової стелі відпуску в точці приєднання немає, тож edge не може обрізати сумарний експорт СЕС + УЗЕ.

**Пропозиція.** Поле стелі експорту в `grid_limits` з **власним значенням для кожного об'єкта**. Звідки береться число — [active_consumer_export_power_cap.md](https://github.com/Agroprosperis/ems-spec/blob/main/docs/specs/active_consumer_export_power_cap.md): самовиробництво — 50 % договірної потужності; УЗЕ не за самовиробництвом — 100 %, але не більше технічного ліміту точки приєднання. Режим не обрано → експорту немає. Так це вже рахується в нашій хмарі з вкладки «Обмеження» кожного об'єкта.

850 кВт у cutover — лише значення для ЖЕ (1 700 кВт × 50 %), не загальна константа.

Окремо: прапорець «заряд УЗЕ з мережі дозволено» (пульт уже має його в «Обмеженнях на весь горизонт»), а `export_allowed` варто явно звузити до продажу з УЗЕ — на надлишок СЕС він не впливає.

## 3. Номер версії і підтвердження від edge

**Що зараз.** cutover §4 вимагає монотонний номер manifest і підтвердження хмарі, що edge застосував; у схемі §8.1 anti-replay прив'язаний до `manifest_id`, який у нас — хеш вмісту, не номер.

**Пропозиція.** Окреме ціле, що строго зростає для об'єкта з кожним новим документом; edge відхиляє номер, не більший за застосований. Підтвердження — подіями в тому ж uplink: застосовано / відхилено (з причиною) / команда почалась / команда закінчилась; поточний номер — у heartbeat.

## 4. `write_enabled` у manifest суперечить cutover

Схема §3.2: `write_enabled: true` → запис у SmartLogger. cutover §4 і handoff §9.1 п. 1: запис відкриває лише локальний прапорець на IoT2050, з хмари він не приходить. Пропонуємо зробити поле в manifest лише інформаційним.

## 5. Порожній план в AUTO

Схема §8 п. 7: `operating_mode=auto` → план обов'язково непорожній. cutover §4: без введеного споживання план за ціною не будується, edge тримає self-consumption за фактом. Пульт так і працює. Пропонуємо дозволити порожній план.

## 6. Відкриті питання

1. **«Не перевищити імпорт».** Це AUTO з лімітом. Від чого edge відштовхується в годинах такого блоку — від `ess_kw` плану (AUTO вже спланований під лімітом) чи від чогось іншого? Якщо базою не буде план, edge нема що обмежувати.
2. **Ціль SOC.** Перегляд у пульті може показувати заряд у найдешевші години блоку, а правило «енергія ÷ час, що лишився» заряджає рівномірно. Ціль та сама, розподіл у часі інший — чи це прийнятно?
3. **Межі команди змінились після підтвердження.** Якщо в «Обмеженнях» знизили ліміт потужності, а збережена команда його перевищує: edge відхиляє весь manifest чи обрізає команду й пише подію? Відхилення всього документа залишає edge на старому плані.
4. «Не перевищити імпорт» у переліку команд тесту запису (cutover §4) відсутній. Підтвердіть, що на першому тесті його не застосовують.
